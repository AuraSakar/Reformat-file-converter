# Release Brief v6: Verify, commit, preview, and deploy Reformat

The Audio tab and the related changes are finished locally and not yet committed. Your job now is to **release them safely**: clean up, commit on a branch, deploy a Vercel preview, verify it, and then, only if every gate below passes, merge to `main` and confirm the production deploy. Do not add features. Do not refactor.

Repository: https://github.com/AuraSakar/Reformat-file-converter (live site: https://reformat-file-converter.vercel.app).

## Ground rules

- Never force-push, never rewrite history, never delete branches other than the one you create, and never commit secrets, `.env` files, `node_modules`, or `dist`.
- Do not turn off Vercel deployment protection, change project settings, or weaken `vercel.json` (especially the CSP) to make a check pass. If a check fails, fix the cause in code, or stop and report.
- If git, GitHub, or Vercel authentication is missing or a command asks for something you do not have, **stop and tell me exactly what is needed**. Do not guess or improvise around it.
- Keep a running log of every command you ran and its result. Include it in the final report.

## Step 1. Pre-flight cleanup (small fixes only)

1. Run `git status` and review every changed and untracked file. Confirm nothing sensitive or generated by mistake is staged.
2. The FFmpeg core files are copied into `public/ffmpeg/` by a prebuild or postinstall script. Confirm that a **clean clone on Vercel will produce them**: the script runs as part of `npm run build` (or install), the `@ffmpeg/core` package is in `dependencies` (not only dev), and `.gitignore` is consistent with that (either the files are committed or they are generated, not half of each). Prove it by deleting `public/ffmpeg/`, running `npm ci && npm run build` in a fresh copy of the repo (or after `git clean`), and confirming `dist/ffmpeg/ffmpeg-core.wasm` exists.
3. Opus is **input-only** now. Search the UI strings, hints, README, and Privacy page, and make sure Opus is never listed as an output format. Output formats shown must match the six that actually work.
4. Silence the harmless Vite chunk-size warning for the lazy HEIC chunk by setting `build.chunkSizeWarningLimit` in `vite.config.js` to just above that chunk's size, with a one-line comment explaining why. Do not split or alter the chunk.
5. Confirm `README.md` lists current formats and mentions FFmpeg (LGPL) and the HEIC library attributions, and that the Privacy page says audio and image processing happen on the device.
6. Run `npm ci`, `npm run build`, and your existing test suites (the 57-case matrix and 61-case edge tests). All must pass. Re-confirm the initial Images route is still under about 150 KB gzipped JS.

## Step 2. Commit on a branch

1. Create the branch `release/audio-tab` from the current `main` (pull the latest `main` first and tell me if it has commits you did not expect).
2. Commit in logical pieces with clear messages (for example: audio tab and engine, HEIC library swap and CSP tightening, release cleanup). Do not squash everything into one vague commit.
3. Push the branch to GitHub: `git push -u origin release/audio-tab`.

## Step 3. Preview deployment

1. Vercel is connected to the GitHub repo, so pushing the branch should create a **preview deployment**. Find its URL through the Vercel CLI (`vercel ls` or `vercel inspect`), through the GitHub deployments status (`gh api` on the commit's deployments), or through the commit status checks. Wait until the build state is **Ready**.
2. If the build fails, read the build log, fix the cause on the branch, push, and wait again. Report what failed.
3. If the preview is behind Vercel Authentication so that requests return 401 or 403, use any supported method the CLI offers to access protected previews. If none works, **stop and tell me**. Do not disable protection.

## Step 4. Verify the preview (all gates must pass)

Run these against the preview URL and record the actual output.

**A. HTTP and header checks (curl -I or equivalent)**
- `/ffmpeg/ffmpeg-core.wasm` returns 200, `content-type: application/wasm`, a compressed encoding (`content-encoding: br` or `gzip`), and `cache-control` containing `immutable` with a long max-age. Report the transferred size.
- `/ffmpeg/ffmpeg-core.js` returns 200 with a long immutable cache header.
- Hashed files under `/assets/` have long immutable cache headers.
- The main HTML response carries the expected security headers: `Content-Security-Policy` (confirm it contains `'wasm-unsafe-eval'` and does **not** contain `'unsafe-eval'`), `X-Content-Type-Options: nosniff`, and `Referrer-Policy`.
- `/`, `/images`, `/audio`, `/pdf/merge`, and `/pdf/text-to-pdf` all return 200 and serve the app (SPA fallback works on direct load and refresh).

**B. Browser tests on the preview (Playwright or similar, headless Chromium, and WebKit as well if available)**
- Zero CSP violation errors and zero uncaught exceptions in the console on `/`, `/audio`, `/pdf/merge`, and `/images`.
- **No third-party network requests.** Record every request origin during the tests and assert that all of them are the preview's own origin (or `blob:` / `data:`).
- Audio: generate a short test WAV (a few seconds of a sine wave plus a second file with different sample rate), then convert in the browser to FLAC, MP3, AAC (M4A), OGG, and ALAC if offered. Confirm each output downloads, is non-empty, and plays or decodes. Also verify a WAV to FLAC to WAV round trip is bit-identical (hash the PCM).
- Test cancel mid-conversion, retry after cancel, and a corrupt file renamed `.mp3` (it must fail on its own row without blocking the others).
- HEIC: convert one HEIC sample to JPG with the strict CSP, confirm no CSP error.
- Images and PDF smoke tests: convert a JPG to WebP, build a 3-image PDF, merge two PDFs, compress a PDF (the output must never be larger than the input).
- Theme: toggle to dark, reload, confirm the choice is remembered and there is no flash of the wrong theme.
- Footer: confirm the four icon links point to the exact URLs in `src/lib/links.js`.
- Mobile emulation: run the Audio and Images flows at 360x800 with a touch device profile and 4x CPU throttling. Confirm there is no horizontal scroll and no failures.

**C. Gate decision**
- If **any** check in A or B fails, fix on the branch, push, and re-run everything. Do not merge on a partial pass.
- If a check cannot be run at all in your environment (for example WebKit is unavailable), list it clearly as **not verified**. That is acceptable only for items that cannot be automated (see "Cannot be verified by you" below).

## Step 5. Merge to main and deploy

Only after every automated gate passes:

1. Merge `release/audio-tab` into `main` with a normal merge (fast-forward is fine). No force push. Push `main`.
2. Wait for the **production** deployment to reach Ready. Confirm it is attached to https://reformat-file-converter.vercel.app (check the alias in `vercel ls` or `vercel inspect`).
3. Re-run the key checks from Step 4 A and B against the production URL: the wasm headers, CSP header contents, SPA routes, console errors, third-party request check, and one Audio conversion (WAV to FLAC) plus one HEIC conversion.
4. **If any production check fails**, restore the site immediately: use Vercel's rollback (`vercel rollback` or promote the previous good deployment), or if that is not possible, `git revert` the merge commit and push (never force-push). Then report what failed and what you did.
5. After a successful production check, leave the branch in place and do not delete anything.

## Cannot be verified by you (list these in your report as remaining for me)

- Real-phone behavior, especially iOS Safari memory with long audio files, and the actual look on a physical screen.
- Real-world download speed of the roughly 30 MB audio engine on a slow mobile connection (report the compressed transfer size you measured, so I can judge it).

## Final report format

Give me a short report with:
1. The commits made (hashes and messages), the branch name, the preview URL, and the production URL.
2. A table of every check in Step 4 and Step 5 with PASS or FAIL and the key measured value (for example the wasm transfer size, the initial JS size, and the cache headers).
3. Anything you fixed during the release and why.
4. Anything not verified, and what I should test by hand on a phone.
5. Whether a rollback was needed.

Do not claim success unless production was checked after deploy.
